01O QUE É RUST
E por que o console foi construído com ele

Rust é uma linguagem compilada: você escreve o código, roda o compilador e ele gera um programa nativo — um .app/.exe de verdade, sem interpretador viajando junto, como em C++. Nada de node embutido.

A promessa dele é ousada: velocidade de C++ com um compilador que recusa programas com chance de erro de memória antes de você apertar F5. Acessar memória já liberada, pisar em ponteiro solto — em Rust, em geral, isso vira erro de compilação, não bug de produção.

No seu mundo (JS/TS)No mundo Rust
node interpreta seu JS em runtimerustc compila para código de máquina nativo
undefined is not a function estoura em produçãoo equivalente estoura na compilação, com a linha certa
null e undefined escapam quando ninguém vênão existem — existe Option, que o compilador te obriga a abrir
try/catch é opcional (e vive esquecido)Result é contrato: a assinatura declara a falha
o teste E2E é a última linha de defesao compilador é a primeira — e nunca fica verde por engano
ANALOGIA DE QA

Você conhece a diferença entre o bug que o Cypress pegou no pipeline e o que o cliente pegou em produção? O compilador de Rust é o estágio de CI mais rigoroso possível: roda antes de tudo, não deixa o merge passar e explica o erro. É o TypeScript estrito elevado à enésima potência — só que caçando bugs de memória, não só de tipo.

Por que um emulador de SNES precisa disso?

60 fps
O loop roda 60 vezes por segundo. Código lento = jogo engasgado. Rust compila tão rápido quanto C++.
Mundo C
O “cérebro” dos jogos (o core snes9x) é uma biblioteca C carregada em runtime. Precisa falar C sem se machucar.
Ponteiros
Frames de vídeo, memória do cartucho, áudio — tudo é buffer. É exatamente onde C++ morde.

03VARIÁVEIS E FUNÇÕES
Rust com picket fence — código real, direto do console

Este método real vive em crates/emulation/src/core.rs e responde “quantos bytes tem um pixel” conforme o formato de vídeo que o core anunciou (leia por cima do match — aula 5):

crates/emulation/src/core.rsrust
impl PixelFormat {
    pub fn bytes_per_pixel(self) -> usize {
        match self {
            PixelFormat::Rgb1555 | PixelFormat::Rgb565 => 2,
            PixelFormat::Xrgb8888 => 4,
        }
    }
}

Tipos explícitos depois de : (parâmetros) e -> (retorno); usize é o inteiro “tamanho natural da máquina”. O estilo é snake_case — e o compilador cobra se você fugir dele. Sem pub na frente, uma função é privada do arquivo. Agora variáveis, de crates/domain/src/rom.rs:

crates/domain/src/rom.rsrust
let header_len = if bytes.len() % 1024 == 512 { 512 } else { 0 };
let rom = &bytes[header_len..];  // fatia: os bytes a partir do header
ANALOGIA DE QA

Se em JS você já aderiu ao “const por padrão, let só quando precisa” — Rust concorda tão forte que inverte: let é imutável como const, e mutabilidade se pede no balcão: let mut total = 0;

DOIS DETALHES QUE CONFUNDEM

1. O if acima produz um valor (vai para header_len) — em Rust, quase tudo é expressão; por isso não existe operador ternário.
2. A última expressão de uma função, sem ponto-e-vírgula, é o retorno. count() sem ; já é o return.

DESAFIO 3 — FORMATADOR DE TAMANHO

Dentro do impl RomId em crates/domain/src/rom.rs, adicione e depois rode cargo check -p sixteen-domain:

pub fn human_size(&self) -> String {
    if self.rom_len >= 1024 * 1024 {
        format!("{:.1} MiB", self.rom_len as f64 / 1048576.0)
    } else {
        format!("{:.1} KiB", self.rom_len as f64 / 1024.0)
    }
}

format! monta texto ({:.1} = uma casa decimal), as f64 converte números e &self é “o próprio objeto”.

04STRUCTS E ENUMS
Modelando o mundo do console

O tipo que representa “a identidade de uma ROM” — o que a estante guarda sobre cada cartucho — é uma struct em crates/domain/src/rom.rs:

crates/domain/src/rom.rsrust
#[derive(Debug, Clone)]           // código gerado de graça (abaixo)
pub struct RomId {
    pub header_len: usize,         // header antigo pulado (0 ou 512)
    pub crc32: String,             // hash que identifica a ROM
    pub internal_name: Option<String>, // título interno, se houver
    pub mapper: Mapper,            // chip de mapeamento do cartucho
}

Cada campo tem nome, tipo e o seu próprio pub. Os comentários /// viram documentação (o cargo doc gera páginas HTML com eles). E o atributo #[derive(...)] pede ao compilador para gerar código entediante: Debug = imprimir no terminal, Clone = copiar, PartialEq = comparar com ==. Detalhe elegante: se a variável tem o mesmo nome do campo (crc32), não precisa escrever crc32: crc32.

E o enum — o tipo do chip de mapeamento e do controle:

rom.rs + emulation/core.rsrust
pub enum Mapper { LoRom, HiRom, Unknown }

pub enum Button { B, Y, Select, Start, Up, Down,
                  Left, Right, A, X, L, R }  // o pad de SNES inteiro

Um valor Mapper é exatamente uma das três variantes — nunca duas, nunca nenhuma, nunca um valor inventado. Não existe mapper = 17 torcendo para ninguém notar: o compilador não deixa. Enums também têm métodos (a bytes_per_pixel da aula 3 era um método do enum PixelFormat).

ANALOGIA DE QA

Em TypeScript você modelaria type Mapper = 'LoRom' | 'HiRom' | 'Unknown'. O enum de Rust é essa união com superpoderes: cada variante pode carregar dados próprios (você verá com os erros, na aula 6) e o compilador conhece a lista completa de casos. Adicione um caso novo e ele aponta todo lugar que precisa se adaptar — como trocar um contrato de fixture e ver o schema apontar cada teste afetado.

05MATCH
O interruptor de trem: exaustivo por lei

match pega um valor e escolhe um ramo conforme ele é — o switch, mas exaustivo: esqueceu um caso, não compila. Este é real — como o emulador decide se a ROM é LoROM ou HiROM:

crates/domain/src/rom.rs · read_internal_headerrust
let lo = title_at(rom, LO);   // título no endereço do LoROM
let hi = title_at(rom, HI);   // título no endereço do HiROM
match (score(&lo), score(&hi)) {
    (l, h) if h > l  => (Mapper::HiRom, hi),   // o hi parece texto?
    (l, _) if l > 0  => (Mapper::LoRom, lo),
    _                => (Mapper::Unknown, None), // ninguém parece
}

Três novidades: match (a, b) casa uma tupla (par de valores); (l, h) if h > l é um padrão com guarda (uma condição extra); e _ é o “qualquer outra coisa”. Padrões também desempacam dados de dentro — o Some(s) abaixo extrai o valor e batiza-o de s:

crates/domain/src/rom.rs · scorerust
fn score(name: &Option<String>) -> usize {
    match name {
        None => 0,
        Some(s) => s.chars().filter(|c| c.is_ascii_alphanumeric()).count(),
    }
}
ANALOGIA DE QA

É o router de comandos do seu app de testes: cada comando tem um handler. A diferença é que aqui, quando amanhã surgir um comando novo e você esquecer dele, o projeto nem compila. O maior match do emulador é assim: dezenas de comandos que o core snes9x manda (emulation/core.rs, função environment_cb), com um _ => false final de “comando desconhecido, não sei responder”.

06OPTION E RESULT
O fim do null e das exceções surpresa

Rust não tem null e não tem exceções. No lugar, dois enums padrão que carregam dados (repare nas variantes com conteúdo):

definições da biblioteca padrãorust
enum Option<T>  { Some(T), None }      // “pode não existir”
enum Result<T, E> { Ok(T), Err(E) }    // “pode falhar”

Option para “pode não existir” (o título interno da ROM — nem toda tem um válido). Result para “pode falhar” (ler um arquivo). A assinatura da função declara a falha e qual o tipo do erro:

crates/domain/src/rom.rsrust
pub enum RomError {
    #[error("could not read ROM {path}: {source}")]
    Read { path: String, source: std::io::Error },
    #[error("file is too small to be a SNES ROM ({0} bytes)")]
    TooSmall(usize),
}

pub fn from_bytes(bytes: &[u8]) -> Result<Self, RomError> {
    if bytes.len() < 0x8000 {
        return Err(RomError::TooSmall(bytes.len()));
    }
    // ... calcula hashes e devolve Ok(RomId { ... })
}

Quem chama não consegue ignorar a possibilidade de erro: para chegar ao RomId, é obrigatório passar pelo Result. E o operador ? é o atalho que você mais usará — de RomId::from_path:

crates/domain/src/rom.rs · o operador ?rust
let bytes = fs::read(path).map_err(|source| RomError::Read { ... })?;
Self::from_bytes(&bytes)  // só chega aqui se o read deu certo

O ? quer dizer: “se deu errado, devolva o erro agora; se deu certo, me dê o valor e siga”. O caminho feliz se escreve como caminho feliz — sem pirâmide de try/catch. Helpers úteis: unwrap_or(padrao) (valor alternativo), and_then(...) (encadear buscas) e take() (pegar o valor deixando vazio — o frame de vídeo usa).

ANALOGIA DE QA

Pense em toda função perigosa devolvendo { ok, valor } — e a linguagem te obrigando a abrir esse objeto antes de usar o valor. O try/catch de JS é opcional e vive esquecido; o Result de Rust é contratual. O Cypress falha o teste no primeiro erro que aparece; Rust falha a compilação no primeiro erro não tratado. Mesma filosofia, estágio mais cedo.

07ITERADORES
Sua esteira de map/filter, agora com fiscal

A coleção cavalo de batalha é o Vec<T> (lista que cresce): Vec<u8> guarda os pixels de um frame, o conteúdo de uma ROM. O array de tamanho fixo também existe — [Button; 12], os doze botões do pad. E o processamento é uma esteira:

crates/domain/src/rom.rs · score, por dentrorust
s.chars()                                   // 1. esteira de caracteres
 .filter(|c| c.is_ascii_alphanumeric())   // 2. só letras e números
 .count()                                  // 3. consome e conta

// o mesmo esquema encaixa etapas até virar lista de novo:
let valid_extensions = cstr.split('|')        // "sfc|smc|swc" → 3 nomes
    .filter(|s| !s.is_empty())
    .map(|s| s.to_ascii_lowercase())          // tudo minúsculo
    .collect::<Vec<String>>();               // esteira → Vec

As |c| ... são closures: funções anônimas — suas conhecidas arrow functions de JS. O modelo mental: a esteira só roda quando alguém consome (count, collect, for); até lá, é preguiçosa e não aloca nada. O filter acima não criou lista intermediária nenhuma.

Em JS você escreveEm Rust, o equivalente
arr.map(x => ...)iter().map(|x| ...)
arr.filter(x => ...)iter().filter(|x| ...)
arr.find(x => ...)iter().find(|x| ...) — devolve Option!
arr.reduce((a,b) => ...)iter().fold(inicial, |a,b| ...)
[...arr].sort() (copia antes)iter().sorted().collect::<Vec<_>>()
ANALOGIA DE QA

É o Array.prototype de JS — só que com o compilador conferindo cada etapa e sem alocação escondida. E repare no find: em Rust ele devolve um Option, porque “não achei” é um resultado possível — nada de undefined escapando pela tubulação.

08POSSE E EMPRÉSTIMO
A chefe final — vá com calma, todo mundo trava aqui
A REGRA DE OURO

Todo valor tem exatamente um dono — e quando o dono sai de cena, o valor é destruído. Não existe free nem coletor de lixo: a memória é liberada no fim do escopo, automaticamente. Quem precisa usar o valor sem ser o dono, empresta:

&T — empréstimo somente leitura. Pode ter quantos quiser ao mesmo tempo.  ·  &mut T — leitura e escrita. Só um por vez, e nenhum & junto.

Por que essas duas regras bastam? Porque praticamente todo bug de memória em C/C++ é alguém escrevendo num dado enquanto outro lê. Com as regras acima, isso não compila. Veja no emulador — o frame de vídeo é o exemplo perfeito:

emulation/core.rsrust
/// Um quadro de vídeo do core.
/// "Owns its pixels."
pub struct Frame {
    pub width: u32,
    pub height: u32,
    pub pixels: Vec<u8>,  // o frame É O DONO
}

impl Drop for Core {
    fn drop(&mut self) { /* desliga o core C */ }
}

O Core entrega um Frame para quem pede (take_frame) — e o frame leva os pixels dele. Quando o frame morrer, os pixels morrem com ele. Zero vazamento, garantido pelo compilador.

E o impl Drop é o destrutor: quando o Core sai de cena, ele avisa o core C sozinho. Ninguém chama retro_deinit “à mão” no app — teardown automático, como uma boa fixture afterEach, só que garantida pela linguagem.

Nas assinaturas do Core, os termos do empréstimo são declarados:

crates/emulation/src/core.rsrust
pub fn system_name(&self) -> &str    // “me empresta o nome, só leitura”
pub fn audio(&self) -> &[i16]       // “me empresta o áudio”
pub fn run(&mut self)               // “preciso me MODIFICAR para rodar”

O compilador garante que ninguém guarda o &[i16] do áudio enquanto chama run() — que limpa e recheia o áudio. O bug de ponteiro pendente que viraria flaky test às 3h da manhã: impossível por construção.

ANALOGIA DE QA

É o modelo de browser context do Playwright levado ao extremo: cada valor tem um dono responsável pelo ciclo de vida (fixture com teardown automático). Vários podem ler ao mesmo tempo (&); se alguém vai escrever (&mut), é exclusivo — sem leitor junto. A data race que você caçaria com retry e café não compila.

SE O COMPILADOR TE XINGAR

Ele é chato como CI vermelho — e útil pelo mesmo motivo: as mensagens apontam a linha, explicam a regra e sugerem a correção.

09MÓDULOS E CRATES
A vitrine do crate — exports de verdade, não convenção

Dentro de um crate, o código se divide em módulos (arquivos). A “vitrine” de cada crate é o lib.rs — ele decide o que a rua vê. Este é o do domain, quase inteiro:

crates/domain/src/lib.rsrust
//! Domain layer: ROM identity, catalogue and No-Intro naming. No SDL.

pub mod rom;         // existe o módulo rom — código em src/rom.rs
pub mod library;

pub use rom::{Mapper, RomError, RomId};   // re-exporta: vitrine
pub use library::{scan, ScannedRom, ROM_EXTS};

pub mod rom; declara o módulo (o arquivo rom.rs que estudamos). pub use rom::RomId; reexporta — é por isso que os outros crates escrevem use sixteen_domain::RomId; e não ...::rom::RomId;. O //! no topo é documentação do módulo. Sem pub? Privado — invisível para fora.

Entre crates, a dependência é declarada no Cargo.toml do consumidor — app declara domain, emulation, platform… por path, igual aos npm workspaces que você já viu em monorepos JS. E as de terceiros (serde, anyhow) são versionadas uma vez só no Cargo.toml raiz, para os seis crates usarem a mesma versão.

O uso, no código do emulador:

crates/app/src/runner.rs · linha 1089rust
match sixteen_domain::RomId::from_bytes(&rom_bytes) { /* ... */ }
ANALOGIA DE QA

É o index.ts de barrel + exports do package.json — só que com privacidade fiscalizada: se você importar algo que a vitrine não exportou, nem compila. Nada de alcançar arquivo interno por caminho relativo e torcer.

DESAFIO 9 — QUEM SABE O SHA-1?

Quando o app chama RomId::from_bytes(...), qual dos dois crates “sabe” calcular SHA-1: o app (que usa) ou o domain (que executa)? Confira: procure sha1 nos dois Cargo.toml. Essa separação — quem usa a informação não é quem sabe calcular — é o motivo do projeto estar fatiado assim.

10TESTES
Sua casa, afinal — unit tests em milissegundos

Testes moram no mesmo arquivo do código, num módulo que só existe quando se roda testes (#[cfg(test)]) — zero custo no programa final. O coração da identificação de ROMs:

crates/domain/src/rom.rs · fim do arquivorust
#[cfg(test)]
mod tests {
    use super::*;   // importa tudo do arquivo de cima

    #[test]
    fn strips_copier_header() {
        let mut rom = vec![0u8; 0x8000];  // ROM “nova” de 32 KiB
        // ... grava um título no endereço 0x7FC0 ...
        let bare = RomId::from_bytes(&rom).unwrap();
        let mut headered = vec![0u8; 512]; // + 512 bytes de lixo
        headered.extend_from_slice(&rom);
        let hd = RomId::from_bytes(&headered).unwrap();
        assert_eq!(hd.sha1, bare.sha1);   // hashes IGUAIS
    }
}
A HISTÓRIA QUE O TESTE CONTA

Cartuchos copiados nos anos 90 vinham com 512 bytes de lixo (header de copiadora) no começo. O teste garante que, com header ou sem, o hash é o mesmo — é isso que faz a sua ROM bater com o banco No-Intro e com o RetroAchievements.

Rodar: cargo test (tudo) ou cargo test -p sixteen-domain strips (um crate, filtrando por nome). O assert_eq! falha mostrando left/right com diff — seu expect().to.equal.

ANALOGIA DE QA

São unit tests em milissegundos — sem browser, sem wait, sem flaky. O “E2E” aqui é abrir o emulador e jogar; o cargo test é a base barata que roda em todo push.

DESAFIO 10 — TESTE O SEU human_size

Da aula 3. Dentro do módulo tests de crates/domain/src/rom.rs:

#[test]
fn human_size_formats() {
    let rom = vec![0u8; 0x8000];   // 32 KiB de zeros
    let id = RomId::from_bytes(&rom).unwrap();
    assert_eq!(id.human_size(), "32.0 KiB");
}

11CHEFES OPCIONAIS
Unsafe, threads e macros — reconhecer já basta (por enquanto)

Você já tem o essencial. Estas são as regiões avançadas do código — a meta aqui é só saber que existem e o que significam quando aparecerem no caminho.

CHEFE 1 — FFI E UNSAFE: A FRONTEIRA COM O C

O filtro de TV conversa com uma biblioteca escrita em C — e o crate emulation carrega o snes9x (.dylib/.dll) em runtime:

crates/ntsc/src/lib.rsrust
extern "C" {                  // funções escritas em C
    fn snes_ntsc_blit(/* ... */);   // o efeito TV de tubo
}

unsafe é o bloco que diz: “a partir daqui, eu assumo a responsabilidade que o compilador não consegue checar”. O projeto os cerca: blocos pequenos, comentados com o porquê (Safety: ...), escondidos atrás de funções seguras.

ANALOGIA DE QA

É o cy.task: sai do sandbox do browser para rodar no Node — poder real, com fronteira documentada. O resto do código de teste continua seguro; o risco fica isolado num lugar só, explicado.

CHEFE 2 — THREADS COM CANAIS

A checagem de update não pode travar o app esperando a internet. Roda numa thread de fundo e responde por um canal:

std::thread::spawn(move || {
    let aviso = check();
    sender.send(aviso).ok();
});

Os dados mudam de dono ao cruzar a thread (aula 8!). A data race simplesmente não compila.

CHEFE 3 — MACROS

Você já viu format!, vec!, assert_eq!. O ! indica macro: código que escreve código na compilação. O projeto define as suas — procure macro_rules! sym em emulation/core.rs: encurta a checagem repetitiva dos 24 símbolos que o core exporta.

E os #[derive(...)] da aula 4? Macros de atributo — você já era fluente e nem sabia.

Último conceito do passeio: traits — as “interfaces” de Rust, um contrato de métodos que um tipo promete ter. Você já as usou sem ver: #[derive(Debug)] implementa o trait Debug, e o impl Drop da aula 8 implementa o trait Drop. Quando bater num impl TraitX for TipoY, já sabe o que é.
